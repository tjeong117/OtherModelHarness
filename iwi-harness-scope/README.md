# Can interpretability help one transformer edit another?

**Proposed first release and experiment · 18 November 2026**

The [19 November follow-up](interpretability-update/README.md) connects the first held-out traces to recent interpretability research and verifies a native neuron-to-weight edit on pretrained Gemma and Qwen.

Give an updater model numerical evidence about a target's behavior. Let it edit the target's weights, then remove the updater and test the saved patch on unseen prompts. The first claim to earn is **higher IWIBench reward from better evidence at a fixed editing budget**. The second is **lower updater token use at comparable edit quality**. These outcomes can move independently.

The updater can be an API model or a locally served open model that issues the same tool calls. The target must have accessible weights and an instrumentable forward pass. The first target should be the text path of Gemma 3 4B IT, pinned to the IWIBench revision. It has both an existing benchmark and a published set of sparse autoencoders (SAEs) trained on the instruction-tuned model. This is a useful intersection of existing assets. [IWIBench](https://github.com/hcltech-robotics/iwibench) · [Gemma Scope 2 for 4B IT](https://huggingface.co/google/gemma-scope-2-4b-it)

## What IWIBench answers

IWIBench gives the editor an objective and public practice, then applies its submitted patch to the pinned base model in a fresh process. Unseen target items measure the requested behavior. Nearby examples, explicit overrides and general controls measure side effects. An alias used correctly in a fresh prompt is already evidence of persistence and within-objective generalization. One standard episode begins at the base with one objective. Learning from yesterday's corrections across a succession of distinct jobs calls for an additional stream experiment. Use the existing benchmark for the first study. [Paper](https://arxiv.org/abs/2611.08647) · [Benchmark methods](https://hcltech-robotics.github.io/iwibench/)

The existing four tools already expose generation, bounded teacher-forced activations and probabilities, weight slices, tensor handles, row copies, outer products and low-rank additions up to rank eight. A successful write invalidates the handles. The pinned implementation can return both a handle and up to 4,096 inline values. That behavior gives us a precise token-efficiency baseline. [Native tensor operations](https://github.com/hcltech-robotics/iwibench/blob/ff1bbcc78f6090e17bf4d50afeb7dc51437b3b53/src/iwibench/tensors.py) · [Limits](https://github.com/hcltech-robotics/iwibench/blob/ff1bbcc78f6090e17bf4d50afeb7dc51437b3b53/src/iwibench/config.py)

The local Etude pilot also sets expectations. Across 21 matched development episodes in eight families, equal-family reward was 0.705 for direct prompting, 0.501 for fixed rank-eight SFT averaged over three seeds, and 0.482 for imported published Sol edits. The paired interval for edits minus SFT crossed zero. Prompting and SFT belong in the results table as alternative ways to achieve the behavior. The test of our new tools is a fresh, paired comparison using the **same updater**. [Etude replication report](../../etude-a1/runs/a1/replicated_deliverables/report.md)

## The first tool surface

Keep the upstream worker responsible for the checkpoint, numerical operations, budgets and patch export. Add an observation layer beside its existing hooks and a thin adapter that emits provider-neutral JSON. On support examples the updater could ask, “When a wrong suggestion flips an otherwise correct answer, which internal changes distinguish those two runs?” It can then test a suspected direction, choose a weight operation, check the result on public examples and submit one candidate.

| Proposed operation | What the updater gets | What the worker does |
|---|---|---|
| Read a weight slice or activation | A short handle, dimensions, checkpoint revision, and optional summary or explicit values | Keeps full precision available server-side. Bounds and charges the slice even when the response is small. Supports paging selected values. |
| Contrast public example pairs | Top candidate layers, MLP channels or SAE features, direction and size of the difference, sample count, representative token spans and handles | Aligns the chat template, tokens and positions, compares like with like, and computes summaries on editor-visible data. Returns evidence of association. |
| Test an intervention | Baseline and intervened answer margins, effect on matched public controls, number of pairs, and forward cost | Temporarily ablates or patches a site on the discovery branch. Removes hooks after the diagnostic. Uses next-token margins for unambiguous single-token choices and length-aware sequence scores for longer alternatives. |
| Write and submit | A receipt with parent and child revision, edited slice, changed scalar count and norm | Applies the existing copy, scale, add or low-rank write. Allows submission of a no-op. Exports numeric replacements for replay on the clean verifier. |

Start with **one contrast and one intervention**, plain PyTorch hooks on a single known site, and one matching Gemma Scope dictionary. Expose raw neuron indices alongside learned features. An SAE feature identifies a direction in an activation space. An individual weight connects an input coordinate to an output coordinate. The two need separate identifiers. Every handle should record revision, layer, site, dimensions and collection recipe. For SAEs also record the dictionary revision and normalization. Check reconstruction error and the unmodified forward pass before interpreting a feature. Invalidate cached observations after a write and remeasure if the updater wants to use the feature again. [Gemma Scope 2](https://huggingface.co/google/gemma-scope-2-4b-it) · [SAELens](https://github.com/decoderesearch/SAELens)

For the first quality comparison, the diagnostics return measurements about candidate sites, and all arms retain the same set of writable tensors and source operands. An example later extension is a typed rank-one operation on a linear map: select an input direction k, an output direction d and a strength α, then add α d kᵀ / (kᵀk + ε) to W. The runtime checks each direction's space and normalization. This makes the change depend on the input's alignment with k. Persist the resulting numbers and verify their downstream effect. If only one treatment can use a new operand or a fitted direction, score that as a separate edit-capability experiment.

**Why verify a proposed mechanism?** Goodfire demonstrated a manual change to a learned parameter component in a 67M model that altered emoticon prediction. The authors describe a deliberately chosen example. Their earlier hosted SAE demo and API have been deprecated. Use their parameter-component work as a design reference, and run the initial SAE diagnostics locally. A causal-tracing study also found that its localization scores failed to predict the best MLP layer for factual rewriting in its experiments. A plausible feature label or a strong temporary steering effect still needs a durable edit and a behavioral test. [Goodfire parameter decomposition](https://www.goodfire.com/research/interpreting-lm-parameters) · [Goodfire service update](https://www.goodfire.com/research/understanding-and-steering-llama-3) · [Hase et al.](https://arxiv.org/abs/2301.04213)

## A measured token example

I serialized the first 256 elements of the embedding row copied by Etude's recorded Gemma alias recipe. These are actual BF16 replacement values. For the read comparison, both responses name the same handle, shape and scalar count. For the write comparison, both operations request the same numerical result on the same base checkpoint.

| One compact JSON payload | Tokens with o200k_base |
|---|---:|
| Read result with 256 inline values and handle | 2,019 |
| The same read result returning the handle alone with its metadata | 23 |
| Replace the slice with 256 literal values | 2,023 |
| Copy the slice from the source row by reference | 45 |

This measures message serialization on one slice. Native IWIBench **already supports** the 45-token copy. The 23-token read is the proposed default; requesting values is still possible. Neither comparison measures total episode savings. Long reasoning, repeated input context, feature descriptions and extra inspection calls can dominate the bill.

## Experiment and decision

Use alias acquisition as a plumbing check. The published row copy should reproduce target behavior after a clean reload, and replaying a recorded action trace under different renderers should reproduce the patch hash. For the first interpretability study, use **resistance to false suggestions**. The target can solve a question unassisted and still accept a confident wrong answer. Pair the same public question under neutral, correct-suggestion and wrong-suggestion wording. An editor that suppresses agreement indiscriminately should lose points on correct suggestions. Use only the public practice items and editor-authored public probes in all arms. Keep calibration cases and grader inputs inside the evaluator. The Etude reproduction found small pristine count mismatches on all three historical resistance episodes, so run every arm against a common freshly measured base and report historical parity separately. [Upstream family implementation](https://github.com/hcltech-robotics/iwibench/blob/ff1bbcc78f6090e17bf4d50afeb7dc51437b3b53/src/iwibench/families_selectivity.py) · [Etude exclusions](../../etude-a1/runs/a1/replicated_deliverables/exclusions.csv)

| Arm | Updater experience | Comparison it answers |
|---|---|---|
| A. Native | Unmodified four-tool IWIBench protocol and serialization | Current reference performance |
| B. Compact | Same numerical reads and writes. A handle is the default response, with explicit value access | B vs A measures the cost and quality consequences of the interface |
| C. Compact + interpretability | B plus contrast and temporary intervention results | C vs B measures whether the diagnostics improve submitted patches |
| D. Matched control | Same tool schemas, output lengths, candidate sites, and probe workload as C. Supply statistics from permuted public pair labels, with the permutation fixed per episode | C vs D tests whether informative measurements contribute beyond tool structure, extra computation or suggestive descriptions |

Keep the updater revision, reasoning setting, decoding, maximum generated tokens, target checkpoint, action space and admissible public prompts fixed. Charge patching passes and controls to the target compute budget; record SAE compute and peak memory. Start with the native ceilings of 8 generation calls, 4 inspection calls and 262,144 target-forward tokens per episode, alongside native sequence limits. Count the component forwards in composite tools. Choose an explicit GPU-time ceiling after timing the pilot. Report both common budget ceilings and actual consumption. For a diagnostic that exceeds the native limits, report an explicitly extended budget and give comparison arms the same opportunity. The official native score and the extended-tool study should be labeled separately. [Native protocol](https://github.com/hcltech-robotics/iwibench)

1. **Pilot on development only.** Run each arm on the same three calibrated development episodes with two updater samples each (24 trajectories). Check replay, headroom, causal-probe alignment, tool-token logs and variability. Inspect cases where raw access helped or the diagnosis led to a worse patch. Use the pilot variance and GPU minutes per episode to set the confirmatory sample size.
2. **Freeze the protocol.** Fix the tool menu, first family, primary comparison, practical effect and retention margins, budgets and rerun rules before opening final outcomes. Use unseen parameter seeds and prompt variants, generated or sequestered before editing. The public historical rollouts are development material. Pair methods on the same episodes, randomize run order and keep failures, no-ops and budget exhaustion in the results.
3. **Score one submitted patch per run.** Primary endpoint is paired C−B difference in native normalized gain × retention. Also report C−D, raw target counts, signed accuracy change, and retention by nearby/general/override slice. The native score clips negative gain, so raw regressions matter. Average editor samples within an episode and estimate paired uncertainty over independent episode seeds. If many seeds share a wording or family, report that limit on generalization.
4. **Test efficiency separately.** Record updater input, cached input, generated/reasoning tokens where exposed, tool-result tokens, schema overhead and cumulative replayed context. Tool-result tokens are a component of input, so avoid double counting. Report target forward tokens, GPU seconds, patch bytes, worst-case context and wall time. Compare B vs A on a fixed replay and on live runs. Then compare quality across common token ceilings, or tokens at a predeclared quality and retention level. A shorter response alone supports only a serialization claim.

A successful first result is a reproducible C−B reward improvement with acceptable control retention at the same budget. A lower-token B that preserves quality is a separate useful result even if C adds nothing. If C beats B but ties D, investigate probe content before attributing the gain to interpretability. Replicate the winning comparison on another task family and a second updater before claiming broader applicability.

## Lambda plan

Budget against the lower estimate of **$4,000 in credits**. A single 80 GB H100 can run the 4B target and a selected SAE; measure peak memory with the actual dictionary and batch. Use a hosted updater for the first paired comparison if its separate API budget is available, or serve an open updater on a second GPU. Keep target workers warm and assign independent episodes to GPUs as concurrency increases. The useful scale axis here is parallel trials. A tightly coupled training cluster becomes relevant when the updater itself is trained.

| Proposed tranche | Example allocation | Planned compute ceiling | Advance when |
|---|---|---:|---|
| Replay and instrumentation | 1× H100 SXM, 12 hours ≈ $51 | $100 | Pristine and known-patch replay pass; identity intervention reproduces logits; accounting is complete |
| Paired pilot | 2× H100 SXM, 48 hours ≈ $402 | $500 | Pilot yields per-arm GPU minutes, editor tokens, variability and enough headroom to size the next run |
| Locked study | 4× H100 SXM, 96 hours ≈ $1,571 | $1,800 | Predetermined held-out cohort and analysis are frozen; confirm that the measured episode cost fits the tranche |
| Replication | Second updater or second family, sized from pilot throughput | $600 | Repeat the most informative comparison, including a negative result if precision is limiting |

The proposed ceilings total $3,000, leaving $1,000–$2,000 for overruns, new hypotheses or later updater training. Example prices use Lambda's on-demand H100 SXM rates of $4.29 per GPU-hour on 1×, $4.19 on 2× and $4.09 on 4×. Instance allocation includes time waiting on a hosted updater. Track billed instance hours, storage, active worker seconds and external API charges separately. These are planning figures; the pilot determines feasible trajectory counts. This scope incurred no Lambda or updater API spend. [Lambda GPU pricing](https://lambda.ai/pricing)

## Follow-on memory experiment

Once the first interface comparison is reproducible, run a stream where a target agent receives feedback about tool conventions. The updater may change the target between jobs. On the next job, start a fresh target context and carry forward only the verified cumulative weight patch. Test new inputs, earlier conventions and unrelated behavior after every change. Compare no update, retrieved experience, direct context, matched-data LoRA and weights plus retrieval. Record update cost and later inference costs across repeated jobs. This is the experiment that can establish where weight updates complement conventional agent memory.
